## 2. Immutable lineage inventory and proposed sidecar

Preserve original source bytes and provenance outside public Git. `EvidenceProvenance.sha256` describes exact persisted raw snapshot bytes only after W2 verifies them against the raw store; a digest cannot establish source truth, rights, or independent collection. Existing inference records carry incident, tenant, evidence, environment, source-dataset, and scenario-family identifiers, but do not encode the ancestry needed here. **Propose a separate restricted, append-only lineage sidecar**, keyed to W1-03 IDs; do not add fields to W1-03 models under this task. A change to those contracts requires a separately reviewed schema amendment. The pending W1-03 deep-immutability repair has its own owner review.

**N-01 rights contract — PENDING OWNER REVIEW.** Every artifact carries a direct `rights_status` (`cleared`, `unknown`, `blocked`) and a separate `rights_basis` (`independent`, `inherited`, `unresolved`). Independently cleared use requires a source-specific rights evidence reference. Verified inheritance requires a named direct parent and a review reference establishing that the parent's permission covers this descendant, transformation, retention, and intended partition/use; the parent must itself be cleared. An inherited artifact may retain direct status `unknown` while its documented inherited clearance is checked transitively. A blocked artifact or a missing/contradictory reference keeps the entire component in quarantine. A default unknown descendant is an unresolved case, **not** an assertion that a license was violated. The current in-process references are caller-supplied assertions; a restricted rights reviewer must verify the underlying license/permission, source, dates, permitted transformations and use before real assignment. Synthetic fixtures state invented clearance/inheritance assumptions explicitly. This inheritance rule, evidence format, reviewer authority and treatment of mixed rights remain proposals.

The sidecar design should contain these entity types and fields, with `unknown` represented explicitly rather than filled by inference:

| Entity | Proposed required identity and ancestry fields |
| --- | --- |
| Original incident | Stable original-incident key, bounded incident/tenant IDs, boundary rationale, source-family and environment candidates, reviewer and source references. |
| Collection and run | Source repository/artifact URL and revision, parent dataset/collection and copy lineage, actual operator and capture/export/acquisition dates, collection pipeline/sensors/configuration, immutable collection ID, run ID and clock/window evidence. A catalog `author` or date is not an operator/capture attestation. |
| Concrete template | Template artifact and revision, exact test/procedure ID, parameterization or configuration digest, payload/variant lineage, and relation to a run. Broad ATT&CK technique or scenario-family text remains a separate descriptor. |
| Source event and snapshot | Original source event ID, incident/tenant and collection/run links, raw-store key, exact-byte SHA-256 and verification state, source time/UTC conversion, immutable snapshot ID, parser/transformation version and parent snapshot ID. |
| Generated or annotated artifact | Artifact type and stable ID; original incident, evidence snapshot and parent artifact IDs; generator/model/prompt/retrieval config IDs and seeds where applicable; creation time; intended population and access class. Includes drafts, atomic claims, pair candidates, gold audit records, operational facts, reports and S2 fork states. |
| Derived perturbation, mutation, or counterfactual | Parent IDs, transform kind/version/parameters/seed, changed evidence availability, human relabel requirement/disposition, and inherited partition. Every descendant remains traceable to an original. |

Represent `same_original_incident`, `same_run`, `uses_concrete_template`, `collected_in`, `contains_event`, `copied_from`, `transformed_from`, and `shares_parent_dataset` as evidence-backed edges. Retain edge source URL/ID/hash, reviewer, decision date, confidence/uncertainty, and supersession history. Corrections append a new version and disposition; they do not mutate a raw snapshot or erase an earlier judgment. Sidecar schema, storage, retention, and roles are **PENDING OWNER REVIEW**.

## 3. Proposed grouping keys and connected components

For a lawful, bounded candidate, construct typed keys from canonical namespace plus source-specific stable identifier; never compare unqualified IDs from different sources. Proposed keys are:

1. `original_incident_key = (source_namespace, original_incident_id)`; all windows or copies of the same original join, even if assigned new local `incident_id`s.
2. `run_key = (operator_or_collection_namespace, original_run_id)`; repeated exports of one execution join. An unknown run ID is `unknown`, not a unique invented run.
3. `concrete_template_key = (template_origin, immutable_revision_or_digest, procedure_or_test_id, normalized_parameterization_digest, variant_parent_id)`. Link executions sharing a documented concrete scenario lineage capable of reproducing the same event sequence, including copied or parameter-varied descendants when review establishes that lineage. A common technique, malware name, emulation-plan title, or `scenario_family` alone creates an **audit flag**, not an automatic edge.
4. `collection_key = (actual_operator, pipeline_or_deployment_id, original_collection_id, capture_campaign_or_parent_id)`. Link events or incidents from the same scenario-producing collection or copied parent collection. A repository name, license, schema, or generic `environment_id` alone is a candidate overlap signal, not proof that records share one concrete collection.
5. `source_event_key = (source_system_namespace, immutable_source_event_id)` and `raw_snapshot_key = sha256(exact persisted bytes)` with source/copy context; equality is reviewed because common boilerplate or hash reuse alone may not prove the same incident.
6. `artifact_parent_key = stable parent artifact ID`; transitive draft, pair, mutation, counterfactual, perturbation, normalization, and report descendants remain with every parent. A derived artifact with parents in two proposed partitions is a contamination finding.

**Proposed algorithm.** Build a private graph of incidents and artifacts; add an edge only for a documented shared identity, copy/parent relation, or independently reviewed concrete run/template/collection relation. Candidate near-matches and broad family signals remain pending edges until adjudicated. Compute undirected connected components over accepted edges before assignment; keep all nodes and descendants of each component in one partition. Add a collection-wide holdout constraint when that collection/environment defines the intended independent holdout, even if not every incident shares a concrete template. Recompute components after any new evidence or descendant; compare old and new component membership and fail the freeze check if an edge would merge different partitions. Do not split a broad dependent component to increase the bootstrap unit count. The exact key normalization, template-equivalence rule, collection boundary, and reviewer protocol are **PENDING OWNER REVIEW**.

An unresolved candidate edge touching different proposed partitions quarantines the affected components from confirmatory held-out A/B until independently resolved. Absence of recorded lineage is not evidence of independence. A false-positive match may be dismissed only with an evidence-backed reviewer disposition; a matching source event, copied snapshot, original incident, run, or concrete scenario-producing collection cannot be waived by renaming hosts or changing schemas.

Compare B candidates against **every** A partition and other B candidates using the §3 graph and §6 overlap audit. A different repository, schema, hostname, IP address, catalog ID, YAML `author`, or date is insufficient. Missing operator, pipeline, run, parent-collection, or rights evidence yields `unknown`/`quarantine`, not an independent-B pass.

## 5. Proposed deterministic assignment and feasibility

No assignment runs in W1. After acquisition and rights/scope/lineage review, create a versioned *candidate inventory* of accepted components and quarantine dispositions. Before any held-out designation, the owner reviews the actual feasible allocation, structural strata and hard exclusions, a fixed seed, and this assignment implementation. The 40/10/15/15 aspiration does not supply those choices automatically. Assignment uses no labels, predictions, draft quality, or test outcomes.

**Proposed reproducibility rule:** canonicalize each accepted component by the lexicographically smallest stable original-incident/collection key among its members; sort A components by the unsigned SHA-256 of the canonical JSON array `[policy_version, seed, canonical_component_key]` under the §9 serializer, breaking hash ties by that key. Reserve approved independent B collections in their entirety for `heldout_b`; never draw B from A by a random label. Process the A list in that order. For each component, choose among `train`, `validation`, and `heldout_a` subject to predeclared source/collection holdout and structural-stratum constraints; select the partition minimizing the sum of absolute deviations from the owner-approved *incident-count* targets after placing the whole component. Break equal scores in the fixed order `train`, `validation`, `heldout_a`. Record each candidate score, chosen partition, seed, policy/code revision, targets, constraints, and component size. No label-based balancing or post-score reseeding is allowed. The fixed tie order and objective are **PENDING OWNER REVIEW**; they are a design proposal, not a frozen algorithm.

Unknown source, run, template, collection, incident boundary, tenant scope, rights, or cross-partition overlap keeps a component in `quarantine`. A reserved source cannot enter A by default. If component sizes, source-family representation, independent units, or B eligibility make the proposed targets impossible, report the achievable allocation and shortfall to the owner **before freeze**. Do not divide a component, backfill with mutations, relabel a development pilot as test, silently choose a new seed, or declare confirmatory feasibility from the incident count alone. Any fallback allocation and design alteration are **PENDING OWNER REVIEW**.

## 6. Duplicate and near-duplicate audit

Run a versioned, privacy-preserving audit within and across train, validation, held-out A and candidate B **before freeze**, and repeat it before W7 unseal. Exact checks cover original/local incident IDs, run and concrete-template keys, collection/parent IDs, source-event IDs, raw-snapshot hashes, derived-parent IDs, draft/pair IDs, and prompt/config hashes. Candidate near-match checks cover normalized evidence text, claim text, source narratives, draft spans, and prompts after a fixed normalization that records case, whitespace, timestamp/entity placeholder handling and language; compare structural source-family and collection overlap separately. A near-match score is a **review trigger**, never an automatic declaration of independent or duplicate lineage. The normalization, candidate algorithm, thresholds and review sampling are **PENDING OWNER REVIEW** and must be fixed on non-test material before held-out inspection.

For each candidate match, store both restricted identifiers, method/version and score or exact key, evidence of shared or distinct ancestry, reviewers, decision (`same_component`, `distinct_with_reason`, `unknown`, `exclude`), timestamp and downstream component effect. Use a second independent reviewer for contested cross-partition or B decisions. Quarantine unresolved overlap; do not merely disclose and retain it in confirmatory test. Record negative audit findings and limitations, including unavailable source hashes or inaccessible parent records. Test content stays with the custodian; development receives only a non-sensitive disposition.

**Pre-acceptance code clarification — PENDING OWNER REVIEW.** Material unresolved overlap across *any two active partitions*, including `train` versus `validation`, blocks a proposed freeze; held-out overlap is a separately reported subset. `reserved`/`quarantine` findings are recorded separately from active cross-partition findings and cannot silently become train/validation examples. A `distinct_with_reason` disposition for a material active match needs an evidence reference and a second distinct reviewer; an exact incident/run/concrete-template/collection/source-event identity remains unwaivable by a text rationale. The current candidate scan retains `SequenceMatcher` and a caller-selected near threshold, with Unicode NFC, case folding and whitespace normalization only. Entity/time placeholder treatment and any changed normalization remain **PENDING OWNER REVIEW**.

The current all-cross-state-pairs scan has quadratic worst-case cost. A provisional explicit comparison budget makes it fail before an oversized scan; that budget is not an approved sample-size or similarity decision. Proposed future indexing: exact-key inverted indexes for structural IDs/hashes and normalized exact text, then predeclared token-shingle blocking for near-text candidates, with exhaustive non-test sensitivity checks for missed candidates. Indexing must not silently change the similarity function or threshold and remains **PENDING OWNER REVIEW**.

**N-02 within-partition independence audit — PENDING OWNER REVIEW.** A separate exact-key index now reports matching tenant/incident scope, original/run/concrete-template/collection/parent-dataset/source-event keys and event hashes between *different* components assigned to the same active partition. It has a distinct provisional candidate-pair cap and report fields; it does not run near-text comparison or infer shared ancestry from generic text. An unresolved, excluded-but-still-active, or `same_component` finding blocks freeze and any claim that those components are independent bootstrap units. A documented `distinct_with_reason` disposition needs evidence and two distinct reviewer references to release that finding; these strings are not authenticated attestations. When review establishes shared ancestry, the custodian adds an accepted reviewed link, rebuilds the graph, recomputes assignments, cluster counts, audit and manifest, and retains the earlier registry as history. Benign shared text alone is not an automatic edge. The exact signal list, cap, review evidence and cluster-resolution standard require owner approval before real data use.

## 7. Inheritance and train-only derivatives

Every normalized snapshot, extracted fact/claim, draft, report, citation, pair and perturbation inherits **all** original-incident and artifact-parent lineage and the parent's partition. No derivative may cross train/validation/held-out A/B. Synthetic claim mutations and counterfactual supervision are `train` only; neither their labels nor descendants may be used as validation or final test pairs. Perturbations R1–R6 retain the original component and partition and are reported separately from independent B. R5/R6 changes to available evidence require human review and relabeling where support changes; never copy an invalid original label. Held-out perturbations may be generated only after authorized unseal under a prelocked diagnostic procedure and cannot tune methods. Any artifact built from parents in different partitions is quarantined and reported as contamination.

## 9. Manifest, checksum, freeze, and amendment proposal

Use versioned, append-only **private** manifests with stable IDs and explicit predecessor hashes. Proposed artifacts are: source/rights inventory; lineage graph and component map; candidate/quarantine and overlap register; split assignment; evidence-snapshot inventory; annotation/blinding audit and sealed gold; W5 draft, candidate and pair-selection manifests; S2 fork archive; W7 configuration/method lock; seal/access log; and evaluation output manifest. A public repository may hold only approved, privacy-safe policy, code revisions and aggregate references. Each restricted manifest records schema/policy version, creator/reviewer, UTC creation time, source revision, status, counts with denominator definitions, and exact referenced artifact hashes.

**Proposed canonical checksum rule:** manifest data use a versioned canonical JSON serializer: UTF-8, Unicode NFC strings, sorted object keys, record arrays sorted by their declared stable record key, positional tuples kept in declared order, no insignificant whitespace, explicit `null` for unknown values, integer counts and decimal strings for non-integer quantities, and no NaN/Infinity. Hash the exact resulting bytes with SHA-256; separately hash exact persisted snapshot, draft and archive bytes. Record serializer version and test vectors before use. A top-level seal manifest references every child manifest ID/hash and approved code/config revision. This rule and the full manifest schema are **PENDING OWNER REVIEW**; no checksum in this document is a dataset seal.

**Pre-acceptance binding proposal — PENDING OWNER REVIEW.** Include the complete assignment-plan identity (seed, targets, minimum components, collection holdouts, policy, algorithm and configuration revisions, and audit-policy digest) even when assignments happen to match another plan. Bind the exact audit revision, threshold, normalization, candidate method, comparison budget and manual dispositions through a canonical audit digest in the proposed manifest. The freeze gate recomputes assignments and findings from the current graph, plan and submitted dispositions, rejecting a stale or altered audit object and any unresolved material active-partition overlap. Direct manifest lifecycle changes do not substitute for that gate. Human approval references in code are audit fields, **not** cryptographic authorization; a real signed seal and isolated storage remain later work.

**N-03 reviewed-link provenance — PENDING OWNER REVIEW.** Sort accepted `ReviewedLink` records by stable endpoints, relation, evidence reference and reviewer, and hash their canonical serialized values together with the registry version, predecessor digest and retained review history. The lineage graph identity and audit subject include this registry digest; the proposed manifest records graph/registry digests and version. Changed review evidence or reviewer identity invalidates old audit and manifest bindings even when component membership is unchanged. An amendment must preserve the prior private registry and link it by predecessor digest; the in-memory model cannot enforce append-only storage or authenticate a reviewer. Registry versioning, decision history schema, sign-off and retention require owner approval.

**Proposed gate sequence:** (1) custodian and independent reviewer resolve provenance, rights, scope, component/overlap, B independence and access exceptions; (2) owner approves feasible split design and restricted assignment; (3) W5 archives the arm-independent generation/pairing procedure and permitted non-test drafts, with any held-out preparation restricted to a separately authorized custodian; (4) W7 locks split IDs, annotation version, prompts/configs, sampling rules, metric/denominator/failure policies and statistical method; (5) W7 completes non-test calibration and mandatory structural/access audits; (6) under scoped, logged custodian access, complete any remaining held-out arm-independent drafts, independently annotated primary pairs and gold critical facts, then checksum and seal exact IDs, gold and pair manifests **before V2/V3 inference**; (7) after method lock, the blinded custodian releases only class/denominator eligibility pass/fail; (8) owner-authorized, logged evaluation access permits conditional held-out A/B runs, archiving and verifying each S2 fork state before its S2/S3 comparison and keeping later output-claim adjudicators blind to arm identity. A failed or unknown gate prevents the affected confirmatory evaluation. No real split or label is frozen in W1.

After freeze, a correction preserves the old seal, records reason, affected IDs, reviewer and impact, and requires a versioned protocol amendment and human approval where it changes protected splits, gold, metrics, denominators, hypotheses, thresholds or test prompts. Any rerun is labeled exploratory or a separately approved amended analysis; never silently overwrite a denominator or relock after inspecting scores. Reviewer, owner, and custodian sign-off identities and exact unseal authority are **PENDING OWNER REVIEW**.

The final held-out candidate/pair manifest records **all** eligible claims, exclusions, a predeclared per-incident cap, sampling seed/probability when capped, population type, ancestry, independent human S/C/I adjudication and annotation audit link. The cap, seed and pairing rules are **PENDING OWNER REVIEW** and pre-test lock. Source-derived or verifier-blind repair diagnostics have separate IDs/manifests; actual V3-directed S3 repair claims belong to E2 and cannot be inserted into the RQ1/RQ3 primary pair population.

RQ2 uses the same held-out incident set and evidence access for S2/S3; archive one hashed S2 state per incident containing retrieval result, initial draft, verification trace and S2 report, then fork S2 and S3 from that identical state. Missing or differing fork states fail the confirmatory paired eligibility rule under the prespecified missing-output policy. Pair/incident exclusions cannot be chosen from arm errors or test scores. The W7 runner records input and output manifests without exposing held-out examples to development.

The preparatory V2/V3 contract now also compares exact ordered claim text and a canonical claim–evidence payload, and verifies the supplied evidence and shared-threshold bytes against their recorded digests. This is a future input-identity guard, not a verifier run or a change to W1-03 pair schemas.

## 11. Non-label structural and later eligibility audits

Before freeze, the custodian computes actual **independent connected-component** counts for each required A/B stratum, incident/component size distributions, source and concrete-family composition, largest-component share, and collection-level dependence. These are structural facts, not inferred from candidate catalog rows, pair counts or gold labels. Check whether broad collection dependence leaves too few independent resampling units; do not split a collection merely to narrow an interval. Record unknown lineage and sensitivity to contested edges. The owner and independent reviewer decide whether the design can support the approved paired lineage-cluster bootstrap and meaningful source/family heterogeneity. The protocol describes the 10-unit/5%-invalid checks as proposed necessary checks, **not** proof of valid confidence intervals.

The restricted B custodian retains exact B counts and releases only a predeclared non-sensitive structural eligibility disposition before locks; any permitted coarsened design description for non-test calibration is **PENDING OWNER REVIEW** and cannot reveal B content or exact held-out IDs/counts for method selection. W7 scenarios use train/validation or designated non-B pilot information and a permitted non-label structural audit, never final labels, predictions, scores or prevalence. W7 first locks the method and completes the approved calibration without sealed gold information. Only after method lock does a blinded custodian check required final gold class availability, non-supported pairs for FSR and eligible gold facts for CFR, releasing pass/fail rather than detailed counts. Failed, inconclusive, infeasible or undefined calibration or eligibility makes the affected RQ exploratory, with no confirmatory claim. Do not claim that a structural count or a passed screening simulation proves nominal coverage, Type I control, or SOC safety.
